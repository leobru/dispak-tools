# PASCODER and overlays

PASCODER proper is the **image writer run after linking**. `P/BOOT` is the
separate, seven-word **reader saved in the resulting image**. `P/CODER` is
their three-word descriptor, generated by `*TABLE`; it is not a library
subroutine. These names had previously been used too loosely in the recovery
notes.

The two object modules were extracted with LIBPUNCH from **2113/1160**, the
PERSO library identified as `13.12.88 ... ПАСКАЛЬ ЗАГРУЗЧИК`:

- [pascoder.madlen](pascoder.madlen): the complete writer, with reconstructed
  labels, symbolic external references, decoded GOST messages and comments.
- [boot.madlen](boot.madlen): the complete saved reader.
- [modules.json](modules.json): object hashes and section sizes.
- [writer-observations.json](writer-observations.json): descriptor words and
  instruction-trace evidence from original-writer invocations.
- [extract.py](extract.py): repeatable extraction and Madlen reconstruction.

```sh
python3 runtime/pascoder/extract.py --extract
```

Extraction uses a private `HOME` and mounts source disks read-only. Objects,
punch cards and listings remain in `runtime/build/pascoder/`. No private disk
hashes are recorded. The regenerated Madlen has not been reassembled.

## PASCODER proper

In the usual link map PASCODER occupies **01000–01777**, 512 decimal words
(half an Э70 page). There are 36 words of executable logic, 16 words of masks,
constants and scratch cells within the object's code section, 25 more words
of constants/messages, and 435 words of BSS. Padding makes the next module
start at **02000**. `MACROBSS`, `P/BOOT`, `P/CODER` and `PROGRAM` are external
dependencies; PASCODER has no overlay-manager dependency.

Offsets in the following table are octal offsets from PASCODER:

| Offsets | Operation |
|---|---|
| `000–002` | Set M8 to self, M9 to `P/CODER`; save the third TABLE word |
| `003–005` | Check the digit fields of the first two TABLE words |
| `006–012` | Convert the destination to an Э70 write word; derive the first memory page from `P/CODER`'s address |
| `013–021` | Convert the zone limit; copy memory cell `017`; compute and check the required zone count |
| `022–024` | Optionally replace the saved stack word using the third TABLE word |
| `025–030` | Write successive memory pages to successive disk zones |
| `031–040` | Print the written zone/word range and execute Э74 |
| `041–043` | Select one of three error messages and use the same print/exit path |

There are **no subroutine calls** in the writer. Its only extracodes are Э70,
Э64 and Э74. It neither enters `PROGRAM` nor loads another program.

### TABLE input is text, not binary integers

For example:

```text
*TABLE:P/CODER(W*660123,L*02)
```

The first two words are eight-character, six-bit **TEXT** words. PASCODER's
APX masks extract the low three bits of each digit character:

| Descriptor word before execution | Characters used | Meaning |
|---|---|---|
| `+0`: `W*660123` | 3–8: six octal digits | Unit `066`, first zone `0123` |
| `+1`: `L*02` | 3–4: two octal digits | Maximum available zones, `02` |
| `+2`: absent/zero, or e.g. `S*40000` | 3–7: five octal digits | Optional saved stack-address replacement |

The first two characters are not interpreted by name: the **word positions**
and masks determine their roles. `S*` above is a descriptive example, not a
recovered historical parameter name. The third word is not digit-validated.

`*TABLE` also appends a zero terminator. With two supplied words this is the
third word, which PASCODER overwrites with N. With a third supplied word the
terminator is a **fourth word** and remains zero after the descriptor. This
explains the extra word at `02012`/`04012` and PROGRAM entry at `02013`/`04013`
in АСС3: the library P/BOOT plus a four-word TABLE occupy eleven words.

The two-digit width of `L` matters. **`L*2` means `20` octal**, because the
following TEXT space contributes a zero digit; `L*02` means two zones. The
existing builders' one-digit limits are therefore larger than their comments
suggest. This has not increased the images written: `L` is a capacity check,
not the number of writes.

### Descriptor output and number of writes

Let `B` be the linked address of `P/CODER`, and let `F` be the low 15 bits of
**memory cell `017`**. This is distinct from index register M17, which is the
writer's current stack pointer.

```text
first_page = B >> 10
last_word  = F - 1
N          = (last_word >> 10) - first_page + 1
```

The shift counts above are decimal. An Э70 page is 1024 words (`02000` octal).
PASCODER rejects `N > L`, then prepares:

| Saved descriptor word | Value |
|---|---|
| `+0` | Э70 write word: `first_page << 30` plus the packed unit/zone |
| `+1` | The **whole contents of cell `017`**, or the third parameter's five-digit value |
| `+2` | Actual page count `N` |

The optional stack replacement happens **after N is computed**. Thus an image
can contain one page while advertising stack start `40000`, or contain many
pages while its saved stack word is zero. It does not change the extent written.

The write loop sends `N` complete pages, adding **0000010000000001** to the
exchange word between pages: increment the memory-page field and disk-zone
field together. It writes through the page containing `F-1`, including the
unused tail of that page. It does not write up to `L`, the catalog allocation,
or a replacement stack address. The live descriptor advances one page/zone
past the end; the descriptor in the first written page retains its initial
exchange word.

### What `02010.L` really comes from

For the usual placement, `B+1 = 02010`. At PASCODER offset `014`, the writer
does `XTS 017; ATX 1(M9)`: it copies the linker's entire word, including its
service fields. PASCODER itself does not calculate the changing left half.
The normal runtime P/1 subsequently uses only the low 15 bits as stack start.

The available Monitor-80 loader source (`utility/loader.txt` in the local
`monitor80-re` checkout, instruction block `PACKDIST`) constructs cell `017`
(`ALF2`) as:

```text
AP | ((LISTEND - BEGLIST) << 30) | ((LOCLIST - LISTMAX) << 15)
```

Consequently the service fields can change with the linker's tables even
when program addresses and FREE are identical. A nonzero third TABLE word
replaces the entire saved word, discarding those service fields.

### Observed original-writer invocation

The original library PASCODER was traced with a one-word PROGRAM, the library
`P/BOOT`, and `*TABLE:P/CODER(W*660123,L*2)`, using a private writable disk.
The trace and listing are in `runtime/build/pascoder/writer-only.trace` and
`writer.lst`:

| Value | Observed result |
|---|---|
| Linked `P/CODER`, FREE | `02007`, `02013` |
| Initial descriptor words | `6712262620212223`, `5412220000000000`, zero |
| Packed destination, packed limit | `660123`, `20` |
| Cell `017` copied into `02010` | `0001220000002013` |
| Actual page count | `1` |
| Э70 write | `0000010000660123` |
| Final message | `ГП ЗАПИСАНА В ЗОНЫ 660123:0000-660123:0012` |
| Exit | Э74 at `01040`; PROGRAM was not entered |

Two further invocations supplied `S*40000` and `S*00000`, both with `L*02`.
They placed PROGRAM at `02013`, FREE at `02014`, and wrote exactly one zone
each. Their saved descriptor words at `02010` were respectively
`0000000000040000` and zero; `02011` was one and `02012` zero in both.
The decks, listings, traces and written images are retained as `stack-high.*`
and `stack-zero.*` in the same build directory. These observations establish
both the stack override and the fourth TABLE word using the original writer.

## P/BOOT: what actually reads an image

P/BOOT receives the **actual first-zone read word in A** from its caller.
The first page has already been read. In abbreviated pseudocode:

```text
M2 = address(P/CODER)
remaining = P/CODER[2] - 1
while remaining != 0:
    A += 0000010000000001
    P/CODER[0] = A
    remaining -= 1
    Э70(P/CODER[0])
    A = P/CODER[0]
jump PROGRAM
```

It does not first load A from the stored descriptor. The caller's A supplies
the **current** unit, zone, memory page and read bit. Hence an image can be
copied to another disk/zone: the reader continues from its actual location,
regardless of where PASCODER originally wrote it. Linked code addresses are
still fixed; this is not relocation of instructions.

P/BOOT changes M2/M3 and A, but preserves the caller's M15 return link and
existing M1/M17. With a count of one it immediately jumps to PROGRAM. It has
no directory of overlays, symbol resolution, switching policy, save area,
stack policy or return-to-caller logic. Those belong to the caller and the
program's startup/runtime.

## How АСС3 overlays use this

The surviving **4001/0132 АСС3** demonstrates the arrangement independently
of the PASCODER object. All addresses and counts below are octal:

| Part | Disk zones | Load address | Descriptor | Saved stack word | Page count | Program entry |
|---|---|---|---|---|---|---|
| Resident head | `0132` | `02000` | `02007` | `40000` | `1` | `02013` |
| Overlay 1 | `0136–0150` | `04000` | `04007` | `0` | `13` | `04013` |
| Overlay 2 | `0152–0167` | `04000` | `04007` | `0` | `16` | `04013` |

The head's main code at **02022** calls **03612** with the running file's
descriptor plus `4`; at **02024** it calls it again with the descriptor plus
`20`. The routine at 03612 stores the supplied read word, extracts its memory
address (`04000`), performs **one Э70**, reloads the exchange word into A and
jumps to 04000. M15 still points back into the head.

Each overlay's ordinary P/BOOT then reads the remaining `12` or `15` pages
and jumps to its own PROGRAM. The overlay's custom P/1 at **27331** or
**36246** keeps the head's **M1 = 02044**, saves the caller/stack state and
installs its own completion routine in `1(M1)`. Completion at **27336** or
**36253** restores the saved stack and returns to the head. The next overlay
overwrites the same 04000 region. The head's stack starts at 40000, above both.

The zero stack words do **not** instruct a generic Pascal runtime to preserve
the stack: these custom P/1 routines implement that behavior themselves.
The head's `40000`/one-page combination and the overlays' zero stack words
are consistent with PASCODER's third parameter. The original build decks have
not survived here, so that specific use of the parameter is an inference.

**Conclusion:** PASCODER can write images used as overlays and can override
their saved stack metadata. The overlay selection, first-page read, shared
globals, stack preservation and return convention are implemented separately.
The generic P/BOOT only completes one contiguous image load.

Catalog allocation lengths must also be kept separate from this page count.
For example, МОНИТР occupies catalog zones `0002–0010` (seven zones), but its
saved descriptor contains `3`: its P/BOOT only loads `0002–0004`. АСС3's
catalog allocation similarly covers all its parts, while the head's descriptor
loads only one zone; the calls at 02022 and 02024 load its other parts.
